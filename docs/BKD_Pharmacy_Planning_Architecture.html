BKD PHARMACY SYSTEM · PLANNING DRAFT01 / 11
01 · Executive brief

One shared pharmacy workflow

A shared system for medicine records, batch-level inventory, pharmacy sales and dispensing, patient and prescription workflows, reporting, and accountable staff access.

CLIENT CONFIRMED

First release foundation

Drug catalogue; stock receiving, balances, and transfers; barcode-enabled POS; fixed selling prices; patient and prescription-linked dispensing; alerts; staff access; reports; and offline sales synchronization.

SCALABLE

Start small, expand cleanly

Begin with the central store and two pharmacy departments. Add pharmacy units and staff accounts later without redesigning the core inventory model.

DECISION TO FINALIZE

Hybrid hosting shape

Client wants fast local operation with a cloud option and VPN access for the MD. This document proposes a local primary server with encrypted cloud backup and recovery capability.

LATER PHASE

Regulatory and hospital integrations

NHIS is deferred. Controlled-drug registers, claims, cashier integrations, and deeper hospital-system links require their own requirements and approval.

Core stock workflow

01 · RECEIVE

Register supplier, invoice, medicine, batch, quantity, cost, fixed selling price, and expiry. Approval workflow is a later enhancement.

02 · STORE & TRANSFER

Track each batch in the central store. Transfer quantities to the selected dispensing department with movement history.

03 · DISPENSE

Search or scan the item, record patient / prescription and payment, print receipt/label, deduct eligible stock.

Physical stock count workflow

1

HOD or store keeper selects a unit. The app snapshots current batch balances and pauses sales, receipts, and transfers for that unit.

2

Pharmacy staff count each batch and enter the physical quantity, including zero. System quantity and variance remain visible.

3

HOD reviews completion and reconciles. The system applies physical balances and retains expected quantity, counted quantity, user, and timestamps.

04 · Proposed architecture

Local speed, cloud recovery

Recommended hybrid pattern for discussion: one local primary system for routine operations, with encrypted cloud backup and a documented recovery path.

Browser on LAN

Staff use the server IP and port 3000. API runs on the same server at port 8000.

Desktop installer

Electron packages the interface and can discover the API on the local subnet. Server and database remain separate.

WAN / cloud

Use VPN for remote users and encrypted backups. Public access, if later required, needs managed HTTPS and security review.

GENERAL HOSPITAL BKD · SYSTEM ARCHITECTURE05 / 11
05 · Network, security & resilience

Operate safely and recover deliberately

These are planning recommendations to validate with the hospital IT team before deployment. Backup objectives and retention are not yet client-approved.

Network boundaries

Keep the API and database on the hospital server network; expose the database only to the API host.
Restrict staff access to hospital LAN; remote MD access uses authenticated VPN with individual accounts.
Use TLS for browser/API traffic where deployed beyond a controlled development LAN.
Separate user roles, disable leavers promptly, and review privileged accounts.

Data protection

Encrypt off-site backups and protect the encryption keys separately from backup storage.
Back up database plus uploaded/configuration assets and document restore steps.
Retain operational audit details for user, time, unit, prior value, new value, and reason.
Test restores regularly and record recovery time, missing data, and corrective actions.

Backup plan to approve

CopySuggested approachPurpose
PrimaryLive hospital server database on protected storage, UPS-backedFast local workflows
Local recoveryAutomated encrypted backup to a separate device/NAS; do not rely on the same diskRecover from operator error or disk failure
Off-site recoveryEncrypted scheduled backup to cloud or a managed recovery environmentRecover from site-level incident
VerificationAutomated completion checks plus documented restore exercisesProve backup can be restored

Decide with hospital IT

Recovery Point Objective (how much recent data can be lost), Recovery Time Objective (how quickly service must return), backup frequency, retention, cloud region/provider, and who can restore.

Offline behavior

POS queues sales locally during an outage. On reconnect, the server validates stock and flags conflicts. It remains the single shared stock authority; independent offline devices cannot reserve the same stock.

10 · Delivery roadmap & decisions

Turn the plan into a safe rollout

Sequence core workflows before integrations. Validate with hospital users using sample data, then stage a controlled pilot.

1 · ConfirmUnit list, staff roles, fixed-price governance, records/import format, and hosting / recovery targets.
2 · PrepareServer, LAN/Wi-Fi, database, UPS, accounts, backup destination, and device compatibility checks.
3 · PilotImport catalogue/stock, train central store and two units, reconcile opening stock, validate POS and counts.
4 · ExpandAdd units/staff, approve terminal connector, expand reporting, then assess NHIS / controlled-drug modules.

Decisions still needed

Cloud provider and backup/standby pattern; backup retention and recovery targets; exact POS terminal/acquirer and integration method; price editing approval and history; stock import columns and data quality; unit names; expiry/low-stock defaults; NHIS/controlled-drug rules.
